## Repository audit (observed)
- Repository: `spyeditz394-dotcom/Realcity-`, default branch `main`; a working branch `part-6-realism-overhaul` was created from `main`.
- Stack in `package.json`: Three.js 0.160.0, Vite 6.4.4, TypeScript 5.8.3, Rapier compat 0.17.3. Scripts: `dev`, `build`, `preview`.
- Entry point: `index.html` loads `/src/main.ts`; `vite.config.ts` targets ESNext and `dist`.
- The game is one large TypeScript entry file with procedural city generation, procedural fallback people, vehicles, touch controls, saving, day/night, quality selection, interiors, and custom kinematic movement/collision checks. Rapier is initialized and used for static overlap queries; the README explicitly says movement is custom kinematic integration rather than full rigid-body dynamics.
- City windows and road markings use `THREE.InstancedMesh`; a number of street/building objects remain individual meshes. Procedural character fallback builds a human-shaped hierarchy from primitives, including face features and finger-like meshes, but that is not proof of a production-quality skinned character.
- The entry point imports `GLTFLoader`, and runtime status strings refer to a rigged asset. The actual asset file, provenance/license, skin weights, animation clips, and rig correctness have **not** been independently verified in this audit.
- HUD fields in source: FPS is computed as frames divided by accumulated `Clock.getDelta()` over about 0.5 s; `JS` is the elapsed main-loop CPU-side work measured around update/render invocation (it is not isolated JavaScript simulation time and includes synchronous render-call overhead); `DC` maps to `renderer.info.render.calls`; `TRI` maps to `renderer.info.render.triangles`; `GEO` and `TEX` map to `renderer.info.memory.geometries/textures`. `MAP≈1MB*` is a hard-coded estimate, not a measured GPU memory reading. The values in the user's screenshot remain unverified observations.
- Startup calls `applyQuality(3)` unless a local saved flag says the character ULTRA benchmark was completed; that path deserves review because a previous saved setting can influence initial selection. No source changes were made yet, so the existing behavior remains untouched.
- Baseline build and live runtime could not be executed through the GitHub source connector alone. No build status, console error list, screenshots, deployment changes, or phone metrics are claimed.

## Key findings and next implementation sequence
1. **Character asset verification is the critical blocker.** Before claiming a real human character, identify the actual GLB URL/path and license, then inspect meshes/materials, skeleton hierarchy, `SkinnedMesh` skin attributes, left/right finger bones, and animation clip names. A HUD bone count alone is insufficient.
2. **Do not treat the procedural fallback as the final realism target.** It has visible primitive-built features and hand/finger meshes, but is not equivalent to a detailed, textured, production rigged asset.
3. **Current NPC goals are broad random world coordinates.** That is likely to send pedestrians across non-walkable spaces despite collision checks; constrain routes to sidewalks and use turn/blocked timers before adding more NPCs.
4. **Performance HUD caveat:** `renderer.info` counters are per-render information; memory geometry/texture counts are resource counts, not bytes. The literal `MAP≈1MB*` label should not be presented as a measurement. JS timing wraps the main loop and render call, so it is not pure simulation time.
5. **Safe implementation order:** validate the existing GLB/animation path and license; fix pedestrian routing and LOD/update scheduling; then add district facade modules and road material improvements; then vehicle visuals; then repeat ULTRA benchmarks. Do not change quality settings to improve the initial baseline.
